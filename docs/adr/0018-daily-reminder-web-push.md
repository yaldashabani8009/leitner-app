# ADR-018: Daily reminder with web push from Supabase

- **Status:** Accepted
- **Date:** 2026-10-29

## Context

Yali asked for a phone notification to practise or add a word. A web app can't schedule a notification on the phone by itself when it's closed (iPhone has no local-notification API for web apps), so a server has to send it. Constraints: free tools only, iPhone Safari and Android Chrome, multi-user ready (RLS), and no personal data or secrets passing through Claude.

## Options considered

1. **Smart daily reminder with web push** (Supabase scheduled job + small server function + web push). Free on Supabase's plan; works on iPhone for the app installed on the Home Screen (iOS 16.4+) and on Android Chrome.
2. **App-icon number only** (Badging API): on iPhone it only updates when the app or a notification runs, so alone it goes stale.
3. **No code**: a daily alarm in the phone's Reminders app. Not smart.

## Decision

**Option 1, with the icon number (option 2) on top** (Yali, 2026-10-29). At **19:00** in the profile's time zone.

- **Rules** (pure, tested, `src/domain/reminder/reminder.ts`): between 19:00 and 23:00 local time, once a day per device. Nothing if today already counts for the streak or the daily cap is reached. Otherwise "N words are waiting for you." or, with nothing due, "Add a word to keep your N-day streak." The icon number is the words still waiting today (`waitingToday`).
- **Database** (`20261029154121_daily_reminders.sql`): `push_subscriptions` (one row per device; RLS: own rows only), `app_config` (the public VAPID key, readable when signed in), `pg_cron` job `daily-reminders` every 15 minutes calling the function through `pg_net`.
- **Secrets never leave Supabase:** the job's password (`reminders_cron_secret`) is generated inside the database, and the VAPID key pair is generated by the function on its first run and stored in Vault (`vapid_keys`). Only the public key is published. The VAPID subject is the app's address, not an email.
- **Server functions** (`supabase/functions/`, Deno): `reminders-cron` (checks `x-cron-secret`, `verify_jwt` off) sends the reminders; `reminders-test` (`verify_jwt` on, so only a signed-in account) sends "Reminders are on" right after turning them on. Both import the pure rules from `src/domain`; `npm run build:functions` bundles each into `functions-dist/<name>/index.js` (part of `npm run check`), which Claude deploys with the Supabase MCP. Library: `jsr:@negrel/webpush@0.5.0` (Web Crypto, made for Deno).
- **App**: after "I'm done for now" on Session complete, "Want a daily reminder?" once per device (yes → the phone's permission prompt → device saved → test notification; not now → again in 7 days; only where push works and permission hasn't been answered). `public/push-handler.js` (loaded into the service worker) shows the notification, sets the icon number and opens the app on tap. While the app is open it keeps the icon number up to date (`useAppBadge`).

## Consequences

- Turning reminders off is done in the phone's settings (there is no settings screen). The server then gets "gone" from the push service and deletes the device.
- Server functions are deployed by hand (MCP), not by GitHub Actions: after changing `src/domain/reminder` or what it imports, rebuild and redeploy them. The first deployment was built just before `waitingToday` was split out of `reminderMessage`; the behaviour is identical.
- In Iran, the phone receives notifications through Apple's or Google's push service, so they may arrive even when Supabase itself is blocked; if the push service is blocked, they simply don't arrive.
- Delivery can't be tested in CI (no push service in headless browsers); unit tests cover the rules and the app side with a fake push service, and Yali tests on the phone.
